# Synthetic reveal bundles for a daily-market forecast

> **SYNTHETIC — not HA-issued.** Every bundle, receipt, closing receipt, key, identifier and timestamp in this
> directory is made up by `generate.py`. The label is also in the data: each `bundle.json` has `synthetic_notice`,
> each receipt and closing receipt has `notice` inside its signed body, and `trust/trust.json`, `expected.json`
> and the TSA root carry it too. A verdict that relies on such a receipt says so (`SYNTHETIC_RECEIPTS_USED`).
> An HTTP 2xx from any server is not a signature and not an independent timestamp, and nothing here is one.

**Synthetic data only.** Nothing here was fetched from, or sent to, Headline Arena (HA) or anyone else: the
agent id (`agent-synthetic-001`), the challenge id (`challenge-synthetic-daily-2026-10-14`), the forecasts, the
timestamp authority, the receipt signer and the sealing key are all generated by `generate.py`, used once and
discarded. No private key is committed (a test checks).

**PROPOSED EXTENSION — not an HA interface.** HA's public interface has no commitment field and no acceptance
receipt (see [`docs/pre-outcome-commitment.md`](../../docs/pre-outcome-commitment.md), Appendix A; HA-4 says there is no
approval or delivery commitment for them, no signing key, no key rotation and no deployment). The `receipts.json`
and `closing.json` files model a *signed counterparty acceptance receipt* and a *signed closing receipt* that HA
does **not** produce; they show what a verifier could establish if a counterparty did. Nothing in this directory
is an HA integration, an HA acceptance fixture or a live forecast, and HA has neither reviewed nor endorsed it.

Family: the **legacy daily directional route** only (`POST /api/v1/eval/challenges/{challenge_id}/predict`), not the
canonical `/api/v1/agent/ha/predict` contract. The payload mapping is `ha-daily-v3`, which is **default-deny**: it
binds all seventeen fields that route declares (OpenAPI 2.2.9), keeps an omitted field, a `null` field and a
present field distinct, and carries numbers as JSON numbers with RFC 8785 serialization (no rounding, no
fractional cap). `probabilities` is an object with exactly `bearish`, `neutral` and `bullish`. The superseded
`ha-daily-v2` (eleven fields, twelve-digit cap) and `ha-daily-v1` are not used here.

## Run the verifier

```sh
python3 examples/ha-reveal/run.py              # all 24 scenarios, prints the table below, exit 0 if all match
python3 examples/ha-reveal/run.py --only m-wrong-agent --only n-wrong-challenge --verbose
```

`run.py` calls the real CLI, `python -m sasana_cli verify-commitment`, once per bundle. To run one by hand:

```sh
D=examples/ha-reveal
T() { python3 -c "import json;print(json.load(open('$D/trust/trust.json'))['$1'])"; }
python3 -m sasana_cli verify-commitment $D/bundles/b-revision-accepted/bundle.json \
  --agent-id "$(T subject_id)" --challenge-id "$(T context_id)" \
  --deadline 2026-10-14T12:00:00Z \
  --tsa-anchor $D/trust/tsa-anchor.pem \
  --receipts $D/bundles/b-revision-accepted/receipts.json \
  --closing-receipt $D/bundles/b-revision-accepted/closing.json \
  --receipt-key "$(T receipt_pubkey)" \
  --mapping ha-daily-v3 \
  --trust-key "$(T seal_pubkey)"
```

Everything the verifier trusts is passed in by you: **whose bundle it must be** (`--agent-id`) and **for which
challenge** (`--challenge-id`), both required and both from your own record of the counterparty, the **deadline**,
the **TSA anchor**, the **receipt key**, the **mapping id** and (optionally) the **sealing key**. None of it is
read from a bundle. Exit codes: `0` VALID_ON_TIME, `1` INVALID, `2` LATE, `3` bad input or unknown or missing flag,
`4` UNREVEALED, `5` VALID_ON_TIME **only under a lenient option** (marked `LENIENT`, never the same as a strict `0`),
`6` INCOMPLETE_RECEIPTS.

## What each bundle shows

Deadline is `2026-10-14T12:00:00Z`. The initial forecast is committed (and timestamped) at 09:00, the revision at
09:30. "Scored revision" is the one the counterparty's signed **closing receipt** names as last accepted before
the deadline, cross-checked against its per-submission receipts.

| Bundle | Situation | Result and why |
|---|---|---|
| `a-initial-only` | One forecast, accepted. | The initial is scored. |
| `b-revision-accepted` | Initial and a revision, both accepted. | The revision (1) is scored; the superseded initial still verifies. |
| `c-revision-rejected` | The counterparty **rejected** the revision. | The **initial** is scored, although revision 1 is also on time in the bundle. Without receipts the verifier would have picked revision 1 (`NO_RECEIPTS` warning). |
| `d-initial-omitted` | Bundle reveals revision 1 but not revision 0. | `INVALID`, `HISTORY_GAP`. Revision 1 commits **inside C** to revision 0's commitment, so the omission is provable. |
| `d2-initial-omitted-lenient` | The same bundle, run with `--allow-unrevealed-history`. | `VALID_ON_TIME` but marked **LENIENT**, exit **5**, `lenient: ["unrevealed history allowed"]` in `--json`. A lenient pass is never mistaken for a strict one. |
| `e-revision-after-deadline-rejected` | Revision timestamped at 13:00 (after the deadline), rejected. | The initial is scored; revision 1's timestamp is not on time. |
| `e2-revision-after-deadline-but-receipt-says-accepted` | Receipt says accepted at 11:59, but the TSA says 13:00. | `LATE`. The scored revision (1) is not provably committed before the deadline; there is **no fall-back** to revision 0, which was not scored. Also `TSA_TIME_AFTER_ACCEPTANCE` (a commitment cannot be submitted before it exists). |
| `f-payload-tampered` | `confidence` edited after commit. | `INVALID`: the commitment does not match the revealed payload. |
| `f2-amount-tampered` | `amount` (the stake) edited after commit. | `INVALID`. Under the superseded `ha-daily-v1` this edit would **not** have been detected. |
| `g-wrong-mapping-version` | Bundle claims the superseded `ha-daily-v1`. | `INVALID`: not the mapping the verifier requires (`ha-daily-v3`). (The mapping id is inside C, so relabelling a payload also changes C.) |
| `h-never-revealed` | The counterparty accepted revisions; nothing was revealed. | `UNREVEALED` (exit 4): neither passed nor failed. |
| `h2-scored-revision-not-revealed` | Revision 0 revealed, but the scored revision is 1. | `UNREVEALED`. |
| `i-operator-reseal-after-commit` | Operator rewrote an event **before** the committed root and had the (throwaway) Archeion seal it. | `INVALID`: the seal verifies as `AUTHORITATIVE_EVIDENCE` under the pinned key, yet `session_root` is no longer in the session. The commitment, not the seal, catches it (threat A8). |
| `j-later-receipt-withheld` | The committer supplies only the initial's receipt and withholds the later accepted one. | `INVALID`: the counterparty's closing receipt says **2** were accepted, last revision 1; the list shows 1, last revision 0 (`RECEIPT_LIST_DISAGREES_WITH_CLOSING`). |
| `k-closing-receipt-missing` | Receipts, but no closing receipt (there is no `closing.json`). | `INCOMPLETE_RECEIPTS` (exit 6): not valid, because the verifier cannot tell a complete list from one with a receipt withheld. |
| `l-closing-receipt-wrong-key` | Closing receipt signed by a key the verifier did not pin. | `INVALID` (`CLOSING_RECEIPT_INVALID`). |
| `m-wrong-agent` | An **honest, fully valid** bundle committed under `agent-synthetic-002`, with that agent's own receipts. | `INVALID`, one reason: `AGENT_ID_MISMATCH`. Only the verifier's own record (`--agent-id`) can say whose bundle it must be; a test shows the same files verify when told that identity. |
| `n-wrong-challenge` | The same, committed under another challenge id. | `INVALID`, one reason: `CHALLENGE_ID_MISMATCH` (kept separate from `m`). |
| `o-wrong-revision-index` | Revision 1's `revision_index` edited to 5. | `INVALID`: the index is inside C, so the commitment no longer matches. |
| `p-corrupted-seal` | One hex digit of the `CHAIN_SEAL` signature flipped. | `INVALID`: the signature is not part of the event hash, so the hash chain is intact and only the seal check catches it (`CHAIN_SEAL signature invalid`). |
| `q-duplicate-revisions` | Revision 1 listed twice. | `INVALID` (`duplicate revision_index in bundle`). |
| `r-reordered-revisions` | The `revisions` array reversed. | **Identical output to `b`.** The verifier orders by `revision_index`, so the array order is ignored (pinned by a test). |
| `s-unstaked-full-vector` | `probabilities` bearish 0.60 / neutral 0.30 / bullish 0.10, **no `amount`**, an **uppercase** 64-hex `prompt_hash` (HA-4's example). | `VALID_ON_TIME`. `amount` is omitted (zero is not an unstaked submission) and `prompt_hash` stays byte-exact. |
| `t-receipt-revision-number-off-by-one` | A receipt numbers revision_index 1 as `ha_revision_number` 1. | `INVALID` (`RECEIPT_REVISION_NUMBER_MISMATCH`): the counterparty counts from 1, the commitment from 0, so revision_index 1 is revision number 2, and the relation is stated, not assumed. |

## Files

| Path | What |
|---|---|
| `bundles/<name>/bundle.json` | The reveal bundle (`bundle_version` 2, `mapping_id`, revisions, the full sealed session, `synthetic_notice`). |
| `bundles/<name>/receipts.json` | Signed per-submission acceptance receipts, **SYNTHETIC, PROPOSED EXTENSION**. Verifier input; never part of the bundle. No `payload_hash` (threat T6). |
| `bundles/<name>/closing.json` | The counterparty's signed **closing receipt**, **SYNTHETIC, PROPOSED EXTENSION**: how many submissions it accepted before the deadline, and which was last. Absent in `k` by design. |
| `trust/tsa-anchor.pem` | The synthetic TSA's root certificate (public). |
| `trust/trust.json` | The verifier's own record: agent id, challenge id, deadline, mapping id, receipt public key (verifies both receipt kinds), sealing public key (all synthetic, all public). |
| `expected.json` | The verdict, effective revision, exit code and a required (or forbidden) message for each scenario (`d2` reuses `d`'s files with an extra flag). |
| `generate.py` | Rebuilds everything with fresh keys and salts (needs `fastapi` and `httpx`). |
| `run.py` | Runs the real CLI over every bundle and prints the table. |

`tests/test_ha_reveal_examples.py` runs the committed bundles, and the generator, against `expected.json`.

## What this does not show

A matching trace is not evidence that the trace is complete or truthful, or that no person influenced the
forecast outside the instrumented process. Session-open commitments are still deferred. The synthetic session's
event timestamps are generation-time clock readings and are not used for any time decision; all time comes from
the timestamp tokens and the receipts. See the note, "What is still open".
